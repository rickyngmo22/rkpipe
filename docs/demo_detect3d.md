# Demo：3D 线框显示（路线 B：2D 检测 + 度量深度）

> 状态：✅ **已实现**（2026-09-17 重写本文件）。当前链路 = `detect` 主任务出 2D 框
> + `aux depth` 模型出米制深度 → 框底接地带采样 → 几何反推 3D 包围盒 → P2 投影画 12 条棱。
>
> **本文档描述当前实现。** 早期基于 KITTI 单目 3D 头的 `detect3d` 任务方案已废弃并清理，
> 其踩坑记录与相机标定方法保留在 `archive/demo_detect3d_kitti.md`（KITTI 旧方案留档，随私有核心仓维护，不在本开源仓）。
>
> P2 主点已于 2026-09-17 从「图像中心」修正为「道路消失点」，见下方 §P2 标定。
>
> **2026-09-17 二次修正（重要）**：基于 901 帧真实检测数据的复核**推翻了两条早期结论**——
> ①「2D 框比车身松 3.8 倍」**不成立**（框实测很紧，帧间抖动 0px）；
> ②「主点偏移会让线框整体平移 94.5px」**不成立**（主点抵消效应，实测平移仅 ~1px）。
> 真正约束 3D 线框的是**单目信息量极限**，已通过 §3D 线框最小绘制距离 落地方案。

## 为什么换掉 KITTI 单目 3D 头

早期方案让模型直接回归 3D 中心偏移、深度、尺寸残差、朝向 bin（MonoCon 风格，KITTI 权重）。
问题：

1. **跨场景泛化差**——KITTI 是德国街景，换到任意相机素材上深度/尺寸系统性失真，
   `detect3d_depth_scale` 只能靠肉眼看线框贴不贴合反复 A/B，**没有物理意义的唯一解**；
2. **真机算子坑深**——工程链接的 librknnrt 2.3.2 有一批仅真机可见的算子 bug
   （GatherElements 索引垃圾、动态 Gather 选列损坏、`Pow` 返回全 0、Exp/Clip 支路通道归零、
   小尺寸 GEMM 列损坏、opt=3 输出边被量化成 int8），解码被迫整段下沉 C++ 并改写图结构；
3. **演示价值低**——未标定相机上数值不可信，最终只能「不显示」。

新方案把「3D」从**模型能力**降级为**几何计算**：模型只负责它本来就擅长的 2D 框和深度，
尺寸/位置由**针孔投影几何**反推，物理意义明确、可解释、可标定。

## 数据流

```
输入帧 (1080p)
   │
   ├─ 主任务 detect  ──→ 2D 框 [x1,y1,x2,y2] + 类别 + conf
   │
   └─ aux 任务 depth ──→ 米制深度图
                          │
                          ▼
        ┌── 接地带采样（ground band）──┐
        │  取框高底部 30% × 宽度中部 60% │
        │  对该区域内深度取中位数 Z      │
        └──────────────┬───────────────┘
                       ▼
        ┌── 几何反推 3D 尺寸 ──────────┐
        │  h = ph · Z / fy             │
        │  l = pw · Z / fx             │
        │  w = l × 0.4158              │
        └──────────────┬───────────────┘
                       ▼
        ┌── 8 角点 → P2 投影 ──────────┐
        │  ry = atan2(sin_alpha,cos_alpha) + θ
        │  得到 12 条棱 → 画线框        │
        └──────────────────────────────┘
```

关键常量与公式在 `include/utils/detect3d_from_depth.h`：

- `kD3WidthRatio = 0.4158f`——车宽/车长先验比（约 1.85m / 4.45m）；
- `h3 = ph · Z / fy`、`l3 = pw · Z / fx`、`w3 = l3 × kD3WidthRatio`。

投影与角点在 `include/postprocess/detect3d_decode.h`：

- `computeDetect3DCorners2D(item, p2, out)`——纯函数，单测覆盖（`tests/test_unit.cpp:326`）；
- **2026-09-02 真机修正**：`ry = atan2(sin_alpha, cos_alpha)`，**不再叠加 `theta`**。
  旧版叠加 `atan2(Z,X)` 导致所有车朝向一致地拧向画面深处，是当时「线框斜着长」的根因；
- `pw > 1e-3f` 后方剔除——投影宽度退化的目标直接丢弃，避免除零后画出天文数字坐标。

## 配置

用 `configs/run_yolo26_detect_depth3d.yaml`：

```yaml
task: detect
model: model/yolo26n.rknn

aux_tasks:
  - task: depth
    model: model/yolo26n_depth.rknn

depth_pseudo: 0            # 关伪彩，输出干净
detect_box_draw: 0         # 关 2D 框，只留 3D 线框
depth_dist_text: 1         # 距离文字
detect3d_wireframe: 1      # 开 3D 线框
detect3d_alpha_deg: 0.0    # 朝向先验（0 = 侧视，路侧车）
detect3d_ground_band: 0.3  # 框底 30% 作为接地带
detect3d_min_depth_m: 8.0  # ★近于此距离的车只画 2D 框（见下方 §3D 线框最小绘制距离）
detect3d_p2: "599.8746 0 990.0000 0 0 599.8746 634.4805 0 0 0 1 0"   # 见下方「P2 标定」
```

跑法：

```bash
./build/console_detector -c configs/run_yolo26_detect_depth3d.yaml
# Web 预览 http://<板子IP>:8090
```

## ⚠️ P2 标定：主点已从「图像中心」修正为「道路消失点」

`detect3d_p2` 是 3×4 行主序投影矩阵 `[fx 0 cx 0; 0 fy cy 0; 0 0 1 0]`。

### 2026-09-17 修正记录

| 项 | 旧值 | 新值 | 原因 |
|---|---|---|---|
| `cx` | 960.0（图像中心） | **990.0** | 人工实测道路消失点（文档原有记录） |
| `cy` | 540.0（图像中心） | **634.48** | 自动估计，多组采样稳定在 634~635 |
| `fx`/`fy` | 600.0 | **599.87** | hfov≈116° 推算（`1920/2 / tan(58°)`），与旧值基本一致 |

**为什么必须改**：相机有俯仰角时，真实主点**不等于**图像几何中心。
本素材实测垂直差 **+94.5px**（折合相机俯仰角约 **+9°**，即略俯视）。
主点在做投影时是纯平移量，所以 cy 差 94.5px 意味着**线框整体上下平移 94.5 像素**
（1080p 上约占画面高度 8.8%）——这就是「看着能用但总觉得不贴地」的主因。

### 怎么估出来的

工具 `tools/estimate_p2_from_video.py`（**新增**，只需已有视频，无需棋盘格）：

```bash
python3 tools/estimate_p2_from_video.py --video test_videos/baseline17.mp4 \
    --frames 150 --hfov 116 --visualize vp_check.jpg
```

原理：Canny + HoughLinesP 检出**通向画面深处的纵向线**（建筑边缘、车道线）→
线对求交投票 → 中位数 + MAD 剔离群。用标注图人工核验。

### ★ 可靠性分级（实测得出，务必理解）

在该素材上分量的可信度**并不相同**：

| 分量 | 表现 | 可信度 |
|---|---|---|
| **cy** | 多组采样数（150/250/300 帧）稳定在 **634~635**，std_y 62~66px；与文档人工实测 630 差 4px | ✅ **可信** |
| **cx** | std_x 214~285px，随采样数漂移 35px（996.7 → 1031.6） | ⚠️ **不可信，需人工核验** |

**cx 为什么不可信**：横向消失点受「车辆自身边缘、非平行建筑、路边招牌」污染，
而这些干扰在 x 方向远大于 y 方向。cy 主要受街道纵深透视线支配，更稳定。

所以本次采取的是 **`cx` 人工实测值 + `cy` 自动估计值** 的组合。
工具会在 `std_x > 150px` 时**主动警告 cx 不可信**，并支持 `--cx-override` 手动修正。

### 工具链一览

| 工具 | 前置条件 | 精度 | 能否自验 |
|---|---|---|---|
| `tools/calibrate_camera.py` | **需现场拍棋盘格** | 最高 | ✅ 有 RMS 重投影误差 |
| `tools/estimate_p2_from_video.py` | 只需已有视频 | 中（cy 可信、cx 需核验） | ⚠️ 出标注图人工看 |
| `tools/estimate_horizon.py` | 只需已有视频 | **本类素材不适用** | ✅ 会自我诊断并拒绝 |

关于第三个工具：它的原理是「地平线 y = cy」，本应与消失点法**独立互验**。
但在本素材上失效——梯度法给 220、天空色法给 916.5，相差 692px，都不可用。
原因：**城市峡谷 + 前车（公交车）遮挡**导致天空可见区域极窄且被切碎，
梯度法把公交车顶边缘误判为地平线。该工具现已加入自我诊断，
分歧 >80px 时明确报告「本素材不适用」而**不给假信心**。

### 仍是估算，不是标定

以上是「两步估算法」的结果，精度不足以称为标定。
**有相机时请用 `tools/calibrate_camera.py` 拍棋盘格**——那是唯一能自验（RMS < 0.5px）的路径。
录好的视频**无法补标定**（标定必须用同一台相机现场拍棋盘格）。

### 棋盘格标定流程（有条件时）

1. 打印棋盘格（9×6 内角点、方格 20~25mm），贴硬纸板压平；
2. 用**实际演示相机**、**与视频相同分辨率**、**固定焦距（关自动对焦）**拍 15~25 张，
   棋盘覆盖画面各区域（尤其四角），每张姿态不同；
3. `python3 tools/calibrate_camera.py --images "calib/*.jpg" --cols 9 --rows 6`
   ——RMS < 0.5px 为佳，脚本直接打印可粘贴的 `detect3d_p2` 配置行；
4. 广角镜头（畸变明显）额外 `--undistort demo.mp4 demo_rect.mp4` 去畸变。

**常见坑**：自动对焦/变焦会让焦距漂移（标定与拍摄必须同焦距）；换分辨率必须重新标定。

### k 是唯一有效旋钮

**`k = fx / detect3d_depth_scale`**（线框大小∝k、左右展开∝1/k）。
fx 与 depth_scale 单独改一个是**简并**的——改 fx 和改 depth_scale 效果等价。
换素材时先调 k，再微调主点。

## ★ 3D 线框最小绘制距离（`detect3d_min_depth_m`，默认 8.0m）

### 结论先行：近距离车的 3D 线框无解，不是参数问题

**单目 + 单个 2D 框无法约束 3D 长方体沿车长方向的延伸。** 一个 2D 框只能可靠约束
「宽 × 高」这个成像面，而车长（4.5m）的方向与像平面几乎平行，其在图像上的延伸
**完全不受 2D 框约束**。距离越近，该延伸的投影越大：

- 出租车 @ **2.4m**（框 384×330）：4.5m 车长投影后线框横向摊开到 **约 6100px**（画面仅 1920px）
- 公交 @ **12.4m**（框 270×222）：同一套公式下线框 **330×247**，与 2D 框偏差仅 60/25px

这不是公式写错，是**信息量极限**——换任何姿态先验、任何尺寸先验都无法同时满足
「线框贴合 2D 框」和「线框是真实米制长方体」。

### 板端实测数据（baseline17_mid30s，901 帧，3355 个 car 框）

「线框宽 / 2D 框宽」比值 —— ≈1.0 表示线框宽度与 2D 框吻合：

| 距离区间 | 样本数 | 比值中位 | 溢出画面比例 |
|---|---|---|---|
| 0–5 m | 632 | 1.38 | **33%** |
| 5–8 m | 1041 | 1.37 | 2% |
| **8–12 m** | 1405 | **1.08** | **0%** |
| 12–18 m | 277 | 1.04 | 0% |

**8m 起线框与 2D 框基本吻合且零溢出**，故默认取 8.0。

### 阈值扫描（门限效果）

| 阈值 | 保留线框比例 | 溢出率 |
|---|---|---|
| 0（旧行为） | 100.0% | 7.5% |
| 5 m | 80.4% | 0.6% |
| **8 m** | **49.7%** | **0.0%** |
| 10 m | 37.5% | 0.0% |
| 12 m | 8.2% | 0.0% |

取 8.0 的取舍：**保留约一半车辆的线框，换溢出率归零**。
近距车并非不显示——它们仍画 2D 框与距离文字，信息不丢。

### 为什么不「收紧 2D 框」解决

曾假设根因是「2D 框比车身松 3.8 倍，裁掉框顶多余量即可」。**实测证伪**：

| 判据 | 实测结果 |
|---|---|
| 稳定轨迹帧间 \|Δ框高\| 中位数 | **0.0px**（最大 3.0px，n=127~402） |
| 几何自洽性（出租车） | 宽法 Z=2.9m vs 高法 Z=2.7m，**相差仅 6%** |

两条**独立**标尺（车宽 1.85m / 车高 1.5m）反推同一距离高度一致，
说明框贴合真实车身——**框没有松**。
早期「3.8 倍」来自手工标注框，且拿「侧视车长投影」的预期去衡量「正后视车」。

### 顺带发现的姿态先验事实

本素材（纽约第五大道）**全是同向行驶车的正后视/斜后视**，不存在文档早期假设的
「路侧侧视停车」场景。量化证据：近距离大框（h>150px）**AR 中位数 1.42**
（侧视应 ≈3.0，正视 ≈1.23）。`detect3d_alpha_deg: 0.0`（侧视）与素材不符。

> 但实测表明：即便把 alpha 改成 90°，近距车线框反而更差（比值 4.4、溢出 80%）。
> 因为正后视下真正无解的是「车长方向」，换姿态只是把溢出从横向换到纵向。
> **这再次印证门限方案（而非姿态调参）才是正解。**

## 已知边界

- **近距离车无 3D 线框（设计取舍）**：`detect3d_min_depth_m` 默认 8.0，近于此距离的车
  只画 2D 框 + 距离文字。这是单目信息量极限下的最优取舍，不是缺陷——见上方专题章节。
- **朝向是全局先验**：`detect3d_alpha_deg` 一个常量套全图。本素材实测为同向车流（正后视为主），
  与默认的 0°（侧视）不符；但实测改 90° 会让近距车更差，故维持 0° 并靠门限规避。
  进一步改进方向：按框长宽比在 0°/90° 间自动选择，或接朝向分类头（**目前证据不支持先做这件事**）。
- **P2 仍是估算值**：主点已修正到消失点（cy 可信、cx 来自人工实测），但 fx 是 hfov 推算值。
  棋盘格标定仍是最优先的后续动作。
  > **注：主点偏移的实际影响远小于早期预估。** 早期写「cy 差 94.5px ⇒ 线框整体平移 94.5px」
  > 是错的——`X = (cu−cx)·Z/fx` 中改 cx 会同时改变反投影 X，投影时又加回 cx，**大部分抵消**。
  > 端到端实测平移仅 **(-0.3, -1.1) px**。**P2 不是当前主要精度瓶颈。**
- **深度精度未量化**：`depth_dist_scale` 与 `near_distance` 目前靠肉眼调，仓库里没有
  「模型输出 vs 卷尺实测」的对照表。**没有这张表，3D 与距离告警的可信度都是悬空的。**
  用户已确认**无现场条件**，故此路径暂时搁置；详见 [`depth_accuracy.md`](depth_accuracy.md)。
- **接地带假设平地面**：坡道、台阶、遮挡会让框底采样点落到非地面像素上，深度偏大或偏小。
- **aux 任务不进主线**：depth 只推理 + 叠加，**不进 TaskResult / tracking / alert / metrics**，
  按设计如此（与 sem 同级）。
- **帧处理走 ensure_bgr 回退**：零拷贝统计会记为 `TaskBgrOnly`（预期行为）。
